2. How to work

  1. Read this page, both workbooks in fixtures/ and the screenshot in design/. Then enter plan mode: propose the stack, architecture, milestone plan and risks. Wait for approval.
  2. One milestone at a time. At the end of each, demo it, run its tests, commit, and stop for review. Do not start the next milestone without a go-ahead.
  3. Measure from the start: a minimal test runner arrives in M3, so every later milestone reports pass rates.
  4. No hard-coding answers to test prompts, no special-casing test IDs, no editing the expected-behavior columns. Report honest pass/fail numbers.
  5. Anything stubbed goes under "Known gaps" in the README.

Base persona (ship as an editable file)

You are Maple Assistant inside the Maple CRM for a mortgage company.
Answer first, in plain words, in the user's language. Never show ids or tool names.
Never guess; look it up. If a lookup is empty or fails, say so and say what you checked.
When the request is clear, do it now. If something required is missing, ask ONE short
question naming it. Find the exact record first; zero matches: say so; several: ask which.
Use only real values from the company's lists. After any change, read the record back and
say what changed, including linked records. New campaigns, drips, pipelines, workflows and
automations start as drafts/off with nobody enrolled; say which. Send, publish or enable only
when asked, with wording you were given. Never message unsubscribed contacts.
You cannot delete, archive, remove or merge: say it has to be done in the CRM, name the record,
offer to list matches, and never work around it. If you have no tool for something, say so and
offer the nearest real option. For several tasks: independent ones together, dependent ones in
order, each under its own label; if one fails, finish the rest and say which part failed.
Social text is drafts only with placeholders, never invented rates, offers, stats, testimonials
or personal data. Say when results are limited to the user's own records or branch.

4. Capabilities (stack-agnostic)

AreaRequirements
Agent loopProvider-agnostic: assemble context, stream the model, run tool calls (parallel when independent), repeat until final answer or a limit (steps, time, tokens, cost). Cancel any time. Usable as a library by routines, subagents and tests.
Events and traceOne typed event stream feeds the UI, run log and Test Lab. Parallel calls share a step id so the trace proves they started together. Every event carries run id and parent run id.
Tools and policyEach tool is classed read, write, live-effect or destructive (inferred from name and MCP hints, editable). Policy per workspace, agent and routine: auto, ask or deny. Defaults: read auto, write auto, live-effect ask (auto only with Owner mode in interactive chat, always denied unattended unless allowlisted), destructive deny. A global deny pattern for delete, remove, archive, destroy, merge beats every allow list.
Tool scopingAbout 300 CRM tools: never in one context. Each subagent sees only its list. Orchestrator gets built-ins plus a few reads, and a tool-search built-in.
Large resultsOver a size limit, store as an artifact, return a summary plus handle, and offer a read-artifact tool. Agents must say how many items they actually covered, never "all" from a sample.
Subagentsspawn_agent and spawn_agents (batch, concurrent). Fresh context per child: system prompt, skills, task, inputs only. Structured result: status (ok, partial, failed, needs_input), summary, data, writes with verified flag, errors, optional single question. Depth and concurrency limits, per-child budgets, no privilege widening. Planner builds a task graph with dependencies; siblings survive each other's failures. Agents refer to model roles (orchestrator, worker, verifier, writer, judge), never to model ids.
Write coordinatorPer-record locking and idempotency keys: identical in-flight creates collapse to one, several changes to one record serialize and none is lost. 10-minute identical-send guard. Automatic read-after-write verification via a per-tool "verify with" mapping.
SkillsFolder per skill with a description and body. Only names and descriptions sit in the prompt; the body loads on demand or is pre-injected per agent. UI to list, edit, test, import and export.
MCPStdio, streamable HTTP and legacy SSE transports; none, bearer, header and OAuth auth; import .mcp.json. Add, test, discover, review tools (enable, class, display labels, verify-with), assign to agents in a matrix. Health checks, reconnect, timeouts, rate limits, plain-language error surfacing, a tool console for manual calls. A disabled "Maple CRM" entry ships preconfigured.
ProvidersAnthropic, OpenAI, Gemini and any OpenAI-compatible endpoint (hosted or local). Add, test (including a tool-call probe), fetch models, set capability flags and prices, map roles to models, fallback chains. Cost and token accounting per run, agent and provider; spend caps; feeds the token meter.
ContextAuto-compaction near 75% of the window, keeping the task, resolved entities and open questions. Session memory of resolved references so "that campaign" works, and asks which when several were just shown.
Security and auditSecrets encrypted at rest and never sent to the browser. Audit log of tool calls, approvals, config changes and routine runs, with secrets redacted. Owner login for v1; respect the CRM user's own permissions. Global kill switch.

7. Loops and routines

Routines: saved, named, triggerable work

A routine is a prompt, an agent, skills, a policy, a trigger, an output and a run history. Triggers: manual, cron (timezone defaults to the CRM company timezone), interval, webhook, CRM event, after another routine. Modes: attended (can ask the user) and unattended (cannot ask; live-effect actions denied unless allowlisted). Every routine has dry run, per-run budget, an overlap lock, a missed-run policy (skip, run once, catch up), retries with backoff, auto-pause after repeated failures, a run key to prevent double-acting, a next-fire preview, and a full stored trace. All seed routines ship disabled.

Loops: repeat until done

Interval (every 15 minutes, check unanswered conversations and draft replies), goal (plan, act, verify until a stop condition holds, such as an automation draft that validates), and watch (poll a cheap read; when it flips, act once). Each has max iterations, cost and time, a stop condition, an on-limit action, a visible countdown and a Stop button. Start from /loop in the prompt box.

8. CRM simulator

A mock CRM tool server with the tool names from section 5, realistic seeded data, and the real CRM's constraints and bugs behind switches, with reset and snapshot/restore. Sends only write to an outbox, never out. Quirks: company lists reject invalid values; no delete tools exist; several branches named San Diego and a transfer to a branch with no agent is refused; a lead and a contact can share one record; unsubscribed contacts vanish from search; tags need existing ids and there is no tag-create tool; the automation list is about 270 KB; the branch list tool fails intermittently; role limits what a user sees (owner 22 conversations, normal user 15); a draft drip cannot be started; a campaign step update can write into the wrong field; duplicate-send guard and token balance; per-user permission gaps such as "cannot create a pipeline".

9. Test Lab

Import every test sheet from both workbooks into rows of: id, module, type, prompt, expected tools, expected behavior, fails-if, depends-on, safety class, original status, comments. Keep the original columns and add result, evidence and run id.

Safety classes. "Safe (read only)" and "Safe (QA record)" run by default. Changes to real records, live effects, real sends and external-platform tests are skipped unless explicitly opted in, and only against the simulator or a confirmed test company. Live runs show a red banner and require typing the company name. Rows marked "same chat, directly after" share one conversation. Modes: run selected, run module, run all safe, re-run failed.

Grading, two layers, both shown. (1) Deterministic checks on the trace and text: tool called or not called (any refuse row fails on a destructive attempt or workaround), parallel calls share a step and dependent ones do not, no confirmation question on clear writes, first line is the finding, X post at most 280 characters, hashtag counts, created campaigns are off with Day 1 and no people, no internal ids, language matches, read-back present. (2) An LLM judge given the prompt, answer, trace summary, expected behavior and fails-if, returning pass, partial or fail with quoted evidence.

Judge calibration. Build a gold set of at least 40 rows labelled by your human testers from the existing Pass/Fail/Partial results. Show judge agreement per module and do not treat judge output as authoritative below 90% agreement. Always show disagreements for human review.

Output. Results table with filters, diff against the previous run, pass rate per module, a regressions banner, export to xlsx and JSON. Regression pack (always run, simulator quirks on): INT-05, INT-44/BR-04, LEAD-12/PSM-07, CON-08/GRP-07, CON-09/10 and SEND-07, CAMP-08, DRIP-06, AUTO-07, CONV-02/06 and INT-14, BR-01, INT-40.

Targets. Simple one-lookup answers in about 12 seconds at the median, five-way parallel requests in about 45 seconds, no timeouts on the eight-way stress case (PAR-27).

12. Inputs to gather before M2

  • Real tool definitions (names, argument schemas, sample responses) from the live Maple CRM MCP server, saved to fixtures/tools/. The simulator must match them, not guess.
  • The current SOUL.maple.md, to diff against the base persona above.
  • The role and permission matrix (owner, loan officer, processor) for the scope tests.
  • Company timezone and a dedicated test company or branch for any live runs.
  • The human Pass/Fail/Partial labels already in the workbooks, for judge calibration.

13. Do not

  • Load all CRM tools into one agent's context.
  • Give any agent a delete, remove, archive or merge tool, even if a server offers one.
  • Let unattended runs send, publish or enable anything that is not explicitly allowlisted.
  • Share conversation history between subagents, or let two writers hit one record without the coordinator.
  • Show ids, raw tool names, secrets or stack traces in normal user-facing text.
  • Run live-CRM or real-send tests without the explicit opt-in.
  • Hard-code test answers or special-case test IDs.
